# lib/ — layout

Feature-based, as the plan's Phase 0 requires and `frontend/CLAUDE.md` details.

| Directory | Holds |
|---|---|
| `core/theme/` | The design tokens (Phase 1): `AppColors`, `AppTypography`, geometry, motion, category accents, and `AppTheme` which assembles the `ThemeData`. Import `app_theme.dart`; reach tokens with `context.colors` / `context.type` / `context.motion`. |
| `core/domain/` | Small domain types more than one feature needs — `VerificationTier`, `ServiceCategory` (🔧 Phase 9 added `suggestedTags`, the step-1 chips §Phase 8 seeds), and Phase 7's `Island` (its `displayName` is the server's: an ambiguous name is qualified `Dh. Meedhoo`, and nothing here rebuilds that rule). |
| `core/categories/` | `CategoryApi` (`GET /v1/categories`, paged to the end) and `CategoriesController`. 🔧 **Moved out of `features/explore/` by Phase 9**, on their second consumer — the wizard's step-1 grid. Nothing changed in the move, and neither holds a fallback list: a hardcoded twelve would hide the failure §Phase 4's Done-when is about. |
| `core/api/` | Phase 3's one HTTP path to the backend: `ApiClient`/`HttpApiClient`, the envelope decode, `ApiException`/`ApiNetworkException`, and the single-flight `ACCESS_TOKEN_EXPIRED` refresh-and-retry. Every feature's data layer goes through this, never `http` directly. |
| `core/auth/` | `AuthController` and the one `AuthState` the root widget switches on (`AuthUnknown`/`AuthGuest`/`AuthSessionExpired`/`AuthSignedIn`); `AuthApi` (the typed `/v1/auth` and `/v1/users/me` calls); `TokenStore` (secure storage); `FormDraftStore` (in-memory, the Session Expired promise's mechanism); `auth_models.dart` (`UserAccount`, `PhoneNumber`, `RegisterRequest`, …). |
| `core/crash/` | `CrashReporter` interface, pulled forward from Phase 21 — Sentry behind it, a no-op with no `SENTRY_DSN`. |
| `core/push/` | Phase 3c. `PushMessaging` — the seam over FCM/APNs, with `UnavailablePushMessaging` behind it because no vendor account exists and **no vendor SDK is a dependency** (`docs/decisions/15-phase-3c-push.md`); `PushController` (registration, token refresh, delivery ack, sign-out cleanup); `PushApi`; `InstallationIdStore` — the stable per-install id a token refresh is keyed on. |
| `core/location/` | Phase 7. `IslandApi` (`GET /v1/islands?search=`, unpaged by §0.0 item 12 — every match, no cap); `islandSearchProvider`, a query-keyed autoDispose family so backspacing reuses the earlier answer; `BrowsingIslandController`, the header's island **held in memory for the session only** and defaulting to nothing; 🔧 Phase 9 added `AccountServiceAreasApi`, which reads the one field the wizard pre-fills step 2 from — **the account-level default, never a listing's own set** (ledger P7-3). Matching, ranking and the display rule are all the server's — this layer sends what was typed and hands back what came back. |
| `core/offline/` | Phase 9. Queue-and-replay, **built once** for the three surfaces §0.0 item 14 allows and no others: the wizard's autosave now, §Phase 17.1's slot/request accept prompt, §Phase 18's chat sends — and **never** the emergency accept. `PendingRequest` is data (`{method, path, body, idempotencyKey, mergeKey}`) rather than a closure, so `FileOfflineQueueStore` can write it to disk and the next launch can send it; `OfflineQueue` records before sending, keeps order, merges writes sharing a `mergeKey`, and surfaces a **server** refusal instead of retrying it forever. |
| `core/media/` | Phase 9. `MediaPicker` — the seam over the platform photo library (`image_picker` is a real dependency: unlike the push and crash vendors it needs no account, and the cover image is required to publish) — and `MediaUploader`, the presigned PUT, which deliberately does **not** go through `ApiClient`: a bearer token, an envelope decode and a session refresh have no business on a signed upload URL. |
| `core/listings/` | Phase 10. `ListingApi` (`/v1/providers/me/listings` — the wizard's calls plus the dashboard's `listOwn`, `setVisibility`, `keepVisible` and `remove`), `ServiceListing` and the listing enums, and `listing_money.dart`'s `customerPricePreview` — the one string both §Phase 9's step 3 and §Phase 10's card print, so the preview a provider is shown is the line a customer reads. 🔧 **Moved out of `features/service_wizard/` by Phase 10**, on its second consumer; nothing changed in the move except four fields the wizard never parsed (`viewCount`, `bookingCount`, `publishedAt`, `updatedAt`), all of them already on §Phase 8's wire. |
| `core/files/` | Phase 10a. `shareProvider` / `shareDocumentProvider` (the OS share sheet) and `tempDirProvider` (an app-private writable directory — `getTemporaryDirectory()`, never `Directory.systemTemp`, which on Android other apps can read). 🔧 **Moved out of `features/account/` on their second consumer**, the invoice PDF: the alternative was the billing feature importing the account feature, which this file forbids. Both injectable, so no test crosses a real platform channel. |
| `core/clock.dart` | `clockProvider`, overridable in tests so a fixed `DateTime` drives OTP/rate-limit countdowns without a real `Duration` wait. |
| `core/format/` | Small display helpers shared across features — `relative_time.dart`'s `shortDate`, `monthAndYear` (Profile's "Member since Jan 2026") and `dayAndMonth` (one end of a billing period, where the year would only repeat); `maldives_time.dart`'s UTC⇄Maldives reading; and Phase 10a's `money.dart` → **`mvr()`, the one place integer laari becomes a string** (`MVR 75`, code first, decimals only where the value has them — never shown as laari). |
| `core/` (later) | Routing, config. No feature may import another feature; they meet here. |
| `features/<feature>/` | One directory per product feature (auth, account, service_wizard, bookings …), each with `presentation/`, `controller/` (Riverpod) and `data/` layers. `features/gallery/` is the Phase 1 component gallery, reachable at `/gallery`. |
| `features/auth/` | Sign In, Register, Verify Email (email OTP, shared by verify-email and change-email via `OtpPurpose`), Session expired, Forgot password (Phase 3b — a six-digit code, not a link). Widgets: `OtpCodeEntry`, `InlineNotice`, `CountdownText`, `AuthHero`, `RoleToggle`, `SocialSignInRow` — `PhoneField` and `genericErrorCopy` moved to `shared/` in Phase 6a, on their third consumer. |
| `features/account/` | Account settings and its sub-screens: Active sessions, Download my data, Delete account, Change password, Change email, Change phone. `AccountController`/`ChangeFormController` (Riverpod). `SettingsRow` moved to `shared/navigation/` in Phase 6, when Profile became its second consumer. |
| `features/notifications/` | Phase 3c. `PushDeniedReminder` — the persistent "You may miss booking requests — enable notifications." notice. Not dismissible, and absent entirely where no vendor is wired in. Provider surfaces mount it; Phase 10's dashboard is the first. |
| `features/legal/` | `LegalPlaceholderScreen` — Terms of Service / Privacy Policy placeholders with no policy prose (root CLAUDE.md invariant 1d); Phase 23 replaces them with real, legally-reviewed copy. `LegalIndexScreen` (Phase 6) is the two-document list Profile's Legal row reaches — navigation only, and it writes no prose either. |
| `features/profile/` | Phase 6. Profile — the customer's account home: the hero, the four booking tiles, the five rows and the role switcher. `ProfileApi`/`ProfileController` over `GET /v1/users/me/profile-summary`; `RoleSwitch` is §Phase 6's last Done-when line as one function — 🔧 **Phase 6a changed its input** from `isProvider` to the server-derived `providerOnboardingComplete`, because the profile is created at onboarding's step 2 and a provider who stopped at step 3 would otherwise never be shown it again. Two things are deliberately not built here: the change-photo control is drawn and inert (no avatar column, and media upload is Phase 8's), and the hero states no location (no customer island until Phase 7). `docs/decisions/18-phase-6-customer-profile.md`. |
| `features/onboarding/` | Phase 6a. **Become a Provider** — three steps behind one route (`/become-a-provider`): the intro, the grouped account details (About you · Getting paid · Availability), and the default service areas. `ProviderOnboardingController` holds which step is showing and makes the two writes; **resume is derived from the server**, so a provider who closes the app reopens on the step their profile says they stopped at, with nothing cached on the device. Step 2 submits on Continue rather than autosaving — the first write creates the provider profile and that flip is permanent. Two things are deliberately not built: the photo control is drawn and inert (Phase 8 owns media upload) and the artboard's atoll chips are absent (the island search already matches an atoll code). `docs/decisions/20-phase-6a-become-a-provider.md`. |
| `shared/` | The shared widgets (Phase 1), one directory per kind — `buttons/`, `cards/`, `badges/`, `chips/`, `inputs/`, `toggles/`, `rating/`, `navigation/`, `headers/`, `avatar/`, `states/`, `sheets/`, `feedback/`, `motion/`. Import them all through `shared/shared.dart`. Phase 6 added three: `navigation/settings_row.dart` and `states/inert_control.dart` moved here when a second feature needed them, and `states/unbuilt_screen.dart` is where a route lands while the phase that owns its screen has not built it. 🔧 **Phase 6a moved two more and added one**: `inputs/phone_field.dart` and `feedback/generic_error_copy.dart` came out of `features/auth/` on their third consumer, and `inputs/field_requirement.dart` holds the Required/Optional pill every delivered form marks its fields with — `AppTextField.requirement` draws it on the label row and appends the word to the spoken label. 🔧 **Phase 10a moved one**: `cards/row_icon.dart`, the accent icon disc a row card leads with, out of `features/my_services/` on its second consumer. 🔧 **Phase 9 moved one and added two**: `navigation/circle_back_button.dart` came out of `features/auth/` on its fourth use and second feature; `states/no_connection_view.dart` is the app-wide no-connection state (§Phase 9 owns it because this is the first phase in which queue-and-replay exists, and therefore the first point at which its explainer is true — **its list of what keeps working offline grows per phase**); and `AppTextField` gained a `prefix` slot for a control drawn inside the field, which `prefixIcon` cannot express because a currency is a word. |
| `features/my_services/` | Phase 10. **My Services** — the provider's workspace at `/provider/services`, where §Phase 6's role switcher has pointed since it was built. `MyServicesController` fetches the four reads behind one skeleton (profile, entitlement cap, listings, catalogue) and owns the mutations; `MyServicesViewController` holds the filter and the list/grid choice so changing either never touches the data. The card is a **container, not a button** — `Pressable` excludes its child's semantics, so a tappable card would erase the menu, the toggle and Finish & publish from the semantics tree; the artboard's card is not tappable either. §1b's over-cap override goes through `POST …/keep-visible`, which sets a pin the server ranks on: the client never writes a visibility the entitlement system owns. `docs/decisions/26-phase-10-my-services-dashboard.md`. |
| `features/billing/` | Phase 10a part 1. **Billing & subscription** (`/provider/billing`), **Pay by bank transfer** and **Invoices** — §1b's manual payment mechanism from the provider's side. `BillingController` holds the three reads behind one skeleton and owns the trial, pause, resume and override mutations; `PayFlowController` holds only what has not left the device (the intent being filled in, the attached receipt); `InvoicesController` and `InvoiceDownloadController` split the list from the per-row PDF fetch. **No billing rule is evaluated here** — Round 19 (§Phase 23) requires the UI to sit behind a boundary thin enough to re-render on the web, so every date and number is a field off `GET /v1/providers/me/subscription`, including the grace end and the period a payment would buy. **Nothing is queued offline** (§0.0 item 14): a failed submission keeps the form and the receipt and offers a live retry, because telling a provider their proof of payment will send when nothing will send it is a false promise about money. `docs/decisions/27-phase-10a-part-1-provider-billing.md`. |
| `features/bookings/` | Phase 17.1. **The booking machine's screens** — `/bookings` (My Bookings, whose pills filter what is already loaded rather than re-fetching, so the count above the list cannot disagree with the list under it), the booking detail with §Phase 17's status timeline and §1h's amendment decision, the payment step, the provider's receipt answer, mark-complete, "Did this happen?", cancel, report a problem, propose an amendment, the provider accept prompt, and `BookSlotScreen` — the rest of `Pick a Time` below the grid, which closes ledger row **P9A-1**. **No screen here draws a way to contact anybody**, not even an `InertControl` where a Message button would go: its own note says a dead tap advertising an action with a person on the other end belongs absent instead. **Exactly one call queues** — the accept (§Phase 17 frontend item 12, §0.0 item 14); a payment claim that failed offline is reported as failed, because telling a customer their "I've paid" is saved when the provider has not received it is a false promise about money. `docs/decisions/28-phase-17-1-bookings.md`. |
| `features/service_wizard/` | Phase 9. The **Create/Edit Service Wizard** — seven steps behind `/services/new`, entered with no arguments for a fresh draft and with a `listingId` to resume one. `ServiceWizardController` owns the step, the debounced per-step PATCH and the publish call; `publish_gate.dart` mirrors the six-field rule **for the header's counter only** (invariant 4 — what publish refuses is what counts). Step navigation is never blocked by validation and Review is always reachable; it waits only on persistence, and offline that wait is instant because the queue accepting the write *is* persistence. Nothing here decides emergency eligibility or the callback guarantee — both are rendered from the server's own answer. `docs/decisions/23-phase-9-service-wizard.md`. |
| `app.dart` | The root widget: the themed `MaterialApp` and the route table. |
| `main.dart` | Entry point only — bootstraps and calls `runApp`. |

`shared/location/` holds Phase 7's two reusable controls, both built standalone rather than for a screen: `IslandSearchList` (the search field and the ranked rows — search **is** the control, 192 islands is not a browsable list, and it never auto-selects a lone match), `IslandMultiSelect` (chips plus the list, embedded by §Phase 6a's onboarding and §Phase 9's wizard step 2) and `IslandPickerSheet` (the header's single-choice sheet). 🔧 **The multi-select now has a screen**: §Phase 6a's onboarding step 3 embeds it, uncapped so the page scrolls the list. The gallery's **Island picker** section stays as the place to exercise it by hand.

Each later phase adds its own feature directory and nothing else. A widget that a second feature needs moves to `shared/`; it is not copied.
